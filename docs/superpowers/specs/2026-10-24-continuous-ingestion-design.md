# Continuous news ingestion

Owner selected continuous processing with all existing checks retained: start the next news lead immediately after a story finishes, rather than waiting five minutes per story. One story/model task remains in flight. Existing reviewed sources, RSS checkpoint intervals, freshness, duplicate/evidence/translation/signature/image requirements and durable holds remain unchanged. This authorizes bounded live workflow/coordinator updates and normal publication; no newsletter sends, paid changes or blanket release of held work.

Approaches: an endless n8n workflow loop risks execution timeout, memory/history growth and queued timer executions; increasing timer frequency alone still inserts a per-story wait. Selected implementation: a lightweight authenticated n8n heartbeat refreshes a single coordinator drain loop. n8n calls once per minute, gets an immediate acknowledgement, and retains no long-running article execution. The coordinator processes published/held results immediately, yielding to the event loop between jobs. Idle, failed, paused, needs-attention, unexpected states and thrown errors stop that drain; a later heartbeat can retry ordinary faults, while durable safety pauses remain enforced by Coordinator.tick.

Implementation calls: each heartbeat authorizes work for75seconds; repeated heartbeats refresh the lease without spawning another loop. When n8n stops, finish only the already-running story once the heartbeat expires, then stop. Idle work wakes on the next one-minute heartbeat. Drain shutdown awaits in-flight work before closing SQLite/runtime resources. Existing manual tick/smoke endpoints remain available with their current single-flight protection. Expose only nonsensitive drain activity in health. Roll out to the dedicated services after tests and one fresh review; verify consecutive run timestamps and live publication/readers where a story passes all checks. Preserve other worktree edits and existing backup/launch monitor schedules.
